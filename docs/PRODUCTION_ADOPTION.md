# Proposed production adoption — NOT EXECUTED

The current deployed API uses an existing Hibernate-managed PostgreSQL schema. Its exact schema, credential configuration and backups have **not been inspected or verified**. No production database connection, baseline, migration, deployment or restart was performed for M2.

## Deployment gate and compatibility risks

Do not deploy this change as a routine JAR replacement. Default configuration now disables Flyway and uses Hibernate `validate`; all five datasource/application credential settings must be explicitly supplied. Missing/blank settings reject startup before datasource beans initialize. Even with correct credentials, Hibernate may reject an incompatible deployed schema. Demo seeding no longer runs by default. The old running process is unaffected until separately approved deployment.

`dev` enables Flyway only for a development database. `postgres-integration` is test-only. `migrated` enables Flyway deliberately; outside dev/test profiles, it additionally requires `app.migrations.approved=true`. `prod` cannot be combined with dev/test profiles. Do not activate development/test profiles on the server or override the schema/migration guards to get deployment working.

`baseline-on-migrate=false` and `clean-disabled=true` are explicit. A non-empty unmanaged schema rejects automatic migration. Enabling Flyway does not constitute approval to baseline an existing database. The approval property is an operator intent gate, not an authorization/security boundary: operators can override configuration, so change review remains necessary.

## V1 design and compatibility findings

V1 creates only `work_orders`: BIGINT identity GENERATED BY DEFAULT, primary key; VARCHAR title(120), description(2000), status(20), priority(10), requester_email(254); DATE due_date; TIMESTAMP(6) WITHOUT TIME ZONE created_at/updated_at. Required fields are NOT NULL; description/due_date nullable. CHECK constraints enforce the application's string status/priority enums. JPA lifecycle callbacks continue supplying timestamps; no database timestamp defaults or timezone conversion introduced.

Fresh disposable PostgreSQL is the verification target. Hibernate validation checks mapping compatibility but is not a complete constraint/index/schema-drift audit. Matching the entity is not proof of matching production. Constraint names/order may differ while semantics match; identity sequence ownership/current values, defaults, column precision, grants, search_path and extensions require explicit inventory. PostgreSQL version of the deployed server is unknown.

## Proposed procedure requiring separate approval

1. **Inventory read-only:** obtain an authorized schema-only dump/catalog inventory of the actual target, including columns/types/nullability/defaults/identity, constraints/indexes/sequences and owners/grants/search_path/extensions/server version. Record deployed artifact and settings by key/presence without exposing credential values. Compare with V1 and the entity; inspect enum validity, required-field nulls and sequence positions using approved read-only queries.
2. **Backup:** agree a maintenance/write-freeze window, take an authorized consistent full backup including relevant role/grant metadata, checksum it, store it securely off-host and record recovery requirements. Avoid copying credentials/client data into Git or this document.
3. **Restore verification:** restore the backup into an isolated non-production rehearsal environment; verify counts, identity inserts, constraints, representative reads/writes and API behavior. A dump file existing is insufficient recovery proof.
4. **Compatibility decision:** if existing schema is semantically identical to V1, consider an explicit, reviewed one-time baseline at version **1** on the restored copy. This marks V1 as represented by the existing schema; it does not execute V1. Baseline at 0 would attempt V1 against existing tables and fail. No blind baseline or `baselineOnMigrate`. If different, stop: design a compatible reconciliation/adoption migration or revise the baseline strategy before deployment, preserving existing data. Do not edit an already-applied migration checksum or use repair to conceal drift.
5. **Rehearse:** test the baseline/adoption command on the restored copy, then application startup, migration validation/history, HTTP contract/security tests, restart/data retention and a subsequent versioned migration as appropriate. Record exact reviewed commands and rollback decisions for the later approval request. Fresh-schema V1 tests remain a separate proof.
6. **Approve and execute separately:** only after review, establish a write freeze and verified backup, confirm target identity twice, baseline/adopt explicitly, and deploy with the intended profiles/approval gate. Never connect these research tests to that database. Prefer separate least-privilege migration and runtime identities in a future deployment design.
7. **Rollback:** retain prior JAR/configuration. Metadata-only baselining may permit artifact rollback, but review interactions with the old Hibernate `update` behavior; do not blindly delete history. Future destructive migrations may make artifact rollback insufficient. Rehearse restore, account for writes after backup, and decide recover-forward versus restore before approval. Avoid a rollback that loses legitimate new data.

## Remaining security concerns

Production credentials were not accessed. Code no longer supplies production default usernames/passwords, but actual deployed values remain unverified. Existing Basic authentication, disabled CSRF and authentication-only write authorization remain unchanged; public reads expose requester email, so this remains a fictional-data portfolio API. Browser identity/roles/CSRF work is outside M2.

Configuration precedence: Spring command-line arguments and external/environment configuration can override packaged properties; active profile order also matters. Production-safe defaults apply without an active profile. Missing/blank required resolved values fail; configured values may be supplied through DB_URL/DB_USERNAME/DB_PASSWORD/APP_USERNAME/APP_PASSWORD or explicit Spring/application properties. Profile mixing is rejected when prod and dev/test coexist. Operator overrides must be reviewed, not assumed safe.
