# M4C local browser authentication design

Reviewed M4B, SecurityConfig, profile safeguards, Compose, CI and production adoption gate before implementation. The chosen architecture uses Spring Security 6.5 formLogin (URL-encoded credentials), IF_REQUIRED sessions, changeSessionId fixation protection and framework logout. A single operator-supplied development user is reused from ignored local Compose settings; no new identity database or roles. Basic is disabled in local-browser. The original non-browser chain and isolated Basic harness remain separate and functional without that profile.

The explicitly enabled local-browser profile may coexist only with dev or test. Credentials must have explicit APP_USERNAME/APP_PASSWORD runtime values; dev fallbacks are rejected. Guard checks reject insecure cookie/profile/transport/database settings. The opt-in Compose override keeps the existing PostgreSQL private and fixes the API host port to 127.0.0.1:8080. Angular is bound to 127.0.0.1:4200. Host and mutation Origin must match the literal loopback design; no CORS origin is granted, Authorization headers are rejected, forwarded headers are ignored. Operators must never deploy either development profile or override file.

Session cookie M4CSESSION is host-only, HttpOnly, SameSite=Strict, Path=/api, with explicit max-age=-1s (no persistent Max-Age); startup rejects a Domain override or persistent cookie age. Timeout is 15 minutes by default, bounded to 1s-15m for expiry verification. Sessions are server-memory state, not persisted across backend restart. Cookies are not isolated by port: run only trusted services on 127.0.0.1. HTTPS requires Secure=true. Local HTTP requires explicit allow-loopback-http=true and Secure=false, accepted only inside the isolated loopback configuration. This is no exception for public deployments.

CSRF applies to login, logout and every unsafe method. Cookie M4C-XSRF is readable by Angular, SameSite=Strict, Path=/ and Secure under HTTPS. The SPA request handler follows Spring's documented 6.5 pattern: XOR/BREACH masking for rendered attributes, plain resolution for cookie-derived request headers, and explicit deferred token loading. The token is never rendered in a response body. Authentication and logout clear the previous token; Angular awaits a new CSRF bootstrap GET after both before more mutations. Default API mutations stay protected by authentication; anonymous mutations return 401, authenticated missing/invalid CSRF and disallowed origins return 403. No POST/PATCH/login/logout automatic retries.

Release frontend builds omit the local provider through file replacement and an independent interceptor rejects local-auth/work-order writes regardless of accidentally supplied providers or hostname changes. The build gate is compile-time, with development mode and exact origin additionally required. The public/default backend denies the local-auth namespace and never registers the local controller/chain. Domain endpoints and Flyway V1 are unchanged; the production migration gate is unchanged.

Sources reviewed: [Spring Security 6.5 SPA CSRF](https://docs.spring.io/spring-security/reference/6.5/servlet/exploits/csrf.html), [form login](https://docs.spring.io/spring-security/reference/6.5/servlet/authentication/passwords/form.html), [logout](https://docs.spring.io/spring-security/reference/6.5/servlet/authentication/logout.html), [Boot 3.5 cookie/session properties](https://docs.spring.io/spring-boot/3.5/appendix/application-properties/index.html), [installed Angular 22 HttpClient CSRF guidance](https://angular.dev/best-practices/security). No public identity management or production security certification is claimed.
